# 可选增强模块

微信基础闭环通过后，把知识库、编程智能体、日常自动化作为三项正式能力升级展示。流程到达用户选中的能力时才读取对应章节，先用普通语言说明“能得到什么、需要什么、用户只做什么”，再完成检测、官网核验、价格与特点对比。只有用户明确选择后才能启用或写入配置；每次只启用一项。

本文件中的裸 `hermes -p <Profile> ...` 只表示普通全新/已授权增量目标的命令形状。受保护验收继续使用 `isolation_guard.py run`，云端全新/小号测试继续使用 `isolation_guard.py run-cloud`，云端 gateway 生命周期才使用 `run-service`。Agent 必须把全部占位符替换为现场核验值并按目标 shell 安全引用，不让用户自己补路径、Profile、ID 或竖线。任何可选项都不能通过换回裸命令绕过基础闭环的根与 HOME 绑定。

进入任何可选能力前，必须继承基础闭环已验收的运行台账：同一个 Hermes 启动器绝对路径、同一个 Hermes 根、同一个 Profile 和同一种执行模式。不得重新搜索 `PATH`、不得因为系统里还有另一个 `hermes` 就换用它，也不得改用 `default` Profile。写入可选能力配置前，先用这份精确台账现场检查所需子命令与安全能力：知识库和编程连接检查 `mcp add --help`与 MCP 运行时，日常自动化检查 `cron --help`、`cron create --help` 和持久回执。当前精确运行时不满足要求时，用中文说明缺少什么，只能在用户同意升级后更新同一环境，或暂停该可选能力；不能悄悄换用另一份新旧不明的 Hermes。

所有 MCP 确认弹窗只描述固定动作、数据流向和后果，不原样回显模型传入的文件名、标题、任务编号或其他未经校验文本，避免工具参数污染授权提示。实际目标继续由安装时白名单、路径校验和私有状态记录约束。

## 1. 知识库

先向用户说明：

> 连接知识库后，助手可以读取、查找和整理你明确允许的资料。知识库不一定是某个软件：它可以是 Obsidian 笔记、飞书云文档，也可以是一个专门存 Markdown 文档的本地文件夹。我们先确定资料在哪里；你选定前，我不会扫描电脑、登录账号或安装 Docker。

第一问必须先展示渠道，不得把用户个人使用过的 Obsidian 当作所有人的默认答案：

> 你的资料现在主要放在哪里？
>
> - **A. 已经在用 Obsidian** — 优先复用现有 Vault，只读取你随后指定的范围
> - **B. 已经在用飞书云文档** — 适合多设备或云端助手，需要飞书官方授权
> - **C. 是电脑里的普通文件夹** — 可以把指定文件夹作为本地知识库，不要求先学 Obsidian
> - **D. 目前没有知识库** — 我会比较“新建本地 Markdown 资料库”和“使用飞书”的成本与难度，再推荐一个
> - **E. 不确定或使用其他工具** — 告诉我你平时在哪里写和找资料，我不会扫描电脑

用户回答前不检查 Obsidian、飞书、目录、同步工具或 Docker，不安装任何依赖。回答后按三种状态分支：

- **已经有**：只申请读取用户选中的那个渠道的非秘密状态，合适就优先复用；不因为列出了其他方案而重复安装。
- **还没有**：本地助手比较“新建一个专用 Markdown 文件夹（¥0，可以后用 Obsidian 打开）”与“飞书云文档”；云端助手优先比较飞书等云文档，不声称能直接读取本机文件。用户选定后才创建或授权。
- **不确定**：只问“你平时在哪里编辑这些资料”，用答案缩小渠道；不得扫描主目录、应用列表或外部账号来猜。

开始检测前必须让用户看懂运行位置的影响：本地助手较容易使用本机资料；云端助手默认看不到本机 Obsidian，需要经过用户选择的同步或云文档方案。没有可验证的目录隔离时，不得把“指定了 Vault 路径”说成“只能访问这个 Vault”。

渠道选定后，先只读取 Hermes 自身的非秘密连接状态。Obsidian vault、同步目录、飞书账号和其他应用只有在用户明确给出检测范围后才读取；不扫描主目录或外部账号。检测后展示：

| 方案 | 最低价格 | 特点 | 云端助手可用性 | 主要限制 | 官方地址 |
|---|---:|---|---|---|---|
| Obsidian 本地知识库 | ¥0 | Markdown 文件、本地掌控 | 不能直接从云服务器读取 | 电脑需在线；只授权指定目录 | [官网与价格](https://obsidian.md/pricing) |
| Obsidian + 官方 Sync | 现场查官网与当前付款页 | 端到端加密、版本历史、多设备同步 | 只有目标环境存在官方支持客户端并实测成功时才算可用 | 不把桌面多设备同步推断成无头服务器支持；付款方式现场核验 | [Sync 与价格](https://obsidian.md/pricing) |
| Syncthing 文件同步 | 软件本身开源免费；设备与网络另计 | 可限定同步目录并排除敏感内容 | 只能提供文件同步，不能自动成为安全任务队列 | 双向删除、冲突副本、权限与版本传播必须先测试；不执行同步文件中的命令 | [Syncthing 官网](https://syncthing.net/) |
| 飞书云文档 | 现场查官网与当前账号权益 | 在线协作、云端访问方便 | 只有 OpenAPI、授权和真实读取均通过时才算可用 | 需要创建应用并授予最小权限 | [版本与价格](https://www.feishu.cn/service-internal)｜[开放平台](https://open.feishu.cn/document) |

当日核对实际价格、免费额度、付款方式、地区与目标系统支持。用户已有 Obsidian 内容时优先复用，但云端不能直接读取本机 vault。任何同步方案都先用测试目录验证创建、更新、冲突、删除和回退，再决定是否接入真实笔记；默认只读并限定具体目录。没有可靠同步时，云端知识库标记未配置。

用户选择“目前没有知识库 → 新建本地 Markdown 资料库”时，Agent 先用普通语言说明将创建的一个新空目录、所在位置和初始费用为 ¥0，并取得这一次创建同意。随后由 Agent 运行 `scripts/scoped_knowledge_mcp.py --root <用户确认的新绝对路径> --initialize-only`；不让用户输入命令。该动作只允许创建一个原本不存在的空目录，成功只返回 `CREATED`，不输出私人路径；目标已存在、上级目录无效、所有者不符或权限无法收紧时全部停止，不复用、不覆盖、不删除任何已有资料。初始化成功后再按下面的只读 MCP 路线连接；`--initialize-only` 绝不写入后续持久 MCP 配置，避免资料库以后被移动或删除时静默重建一个空目录。

Docker 是本地目录的可选硬隔离层，不是知识库。只有用户已经选定本地文件渠道，而且当前工具无法证明目录硬边界时，才解释并比较“安装 Docker 只挂载批准目录”“改用飞书云文档”“明确接受当前系统账号文件权限后进入高风险审查”三条路；小白默认推荐 Docker 或飞书。不得在渠道选择前把 Docker 当成前置问题。

### 撤销知识库访问

用户说“不要再访问”时先立即停止所有相关读取、写入和后台同步，再定位真实授权机制。口头答应、修改 SOUL 或从能力清单删除都不等于撤权。

统一顺序：

1. 记录需要撤销的准确目录、共享或应用授权，不扩大到其他知识库。
2. 暂停对应任务和同步，避免撤权过程中继续读取。
3. 按实际机制移除路径、挂载、共享或 OAuth scope（OAuth 授权范围），然后重载配置或重启受影响组件。
4. 创建新会话，用原路径或原文档做负向测试；**撤权后的读取必须被拒绝**。若仍能读取，保持停用状态并继续定位缓存、重复挂载或另一份授权。
5. 告知用户：撤销后不再允许新访问，但已经进入会话历史、日志、同步设备缓存或模型/工具提供商记录的数据不会被自动抹除；需要删除时按对应系统另行处理。
6. 撤权误伤其他已授权内容时，只恢复用户确认的最小范围，不恢复被撤销目标。

各方案的硬动作：

- **Obsidian 路径**：移除 `OBSIDIAN_VAULT_PATH` 或 Skill 中该绝对路径的授权；检查没有父目录或同一路径的第二份配置；新会话读取原测试笔记必须失败。
- **Obsidian Sync**：先从目标 Hermes 环境移除本地同步目录授权，再在 Obsidian 官方客户端停止该设备或 vault 的 Sync；按用户要求处理本地缓存，不能默认删除笔记；新会话读取原路径必须失败。
- **Syncthing**：在双方设备撤销该 folder ID 的共享或暂停后移除目标目录挂载；先说明删除传播风险，不以删除真实笔记作为撤权手段；新会话读取原同步目录必须失败。
- **飞书 OAuth**：在 Hermes 移除对应 MCP/OAuth 连接，并在飞书开放平台撤销用户授权或缩减应用 scope；刷新 token 失效后重测指定文档，读取必须返回权限拒绝而非缓存内容。

### Obsidian

Hermes 自带 Obsidian Skill。先确认当前安装：

```bash
hermes -p <Profile> skills list --source builtin
```

让用户选择具体 vault，不扫描整个主目录。将解析后的绝对路径写入当前 Profile 的 `.env`：`OBSIDIAN_VAULT_PATH=<vault 绝对路径>`——这是 Hermes 内置 Obsidian Skill 的约定变量，从 `.env` 加载；未设置时它会回退到 `~/Documents/Obsidian Vault`。必须使用本 Skill 的 `scripts/set_profile_env_key.py --profile <Profile> --key OBSIDIAN_VAULT_PATH --value <vault绝对路径> --hermes <HERMES绝对路径> --expected-hermes-root <已批准Hermes根绝对路径>` 幂等更新：它只允许这个非秘密键，保留其他行，不输出路径或环境内容，并把重复键收敛为一个。严格隔离模式通过 `isolation_guard.py run-checker --checker set_profile_env_key.py` 执行。更新后重跑带同一 expected root 的 `check_profile_safety.py`；失败就停止，不得直接 `echo >> .env` 或反复追加。不要把路径变量直接交给文件工具。

`OBSIDIAN_VAULT_PATH` 只是寻址约定，不是权限边界。Profile、SOUL 和 `terminal.cwd` 也都不是沙箱；在本地后端启用通用 `file` 或 `terminal` 后，助手仍可能访问当前系统账号能访问的 Vault 外文件。不得仅凭这个变量就告诉用户“只授权了该 Vault”。小白路线必须优先使用当前版本已经现场证明的隔离方案，例如 Docker 只挂载用户批准的目录并保持宿主 `terminal`、通用文件工具和无关 MCP 关闭；没有可验证的硬边界时停止本可选项，或者在用户明确接受“等同当前系统账号文件权限”的风险后转入独立高风险审查，不能静默放宽。

权限顺序：

1. 先只读列出用户指定文件夹。
2. 读取一篇用户指定笔记。
3. 用户明确同意后，创建或修改一篇可恢复的测试笔记。
4. 不读取 `.obsidian` 中与当前任务无关的插件配置、缓存或秘密。
5. 创建新会话，用 Vault 内测试文件证明允许动作成功，再用 Vault 外专用诱饵证明工作区外读取和写入都被拒绝；任一越界成功都立即停用并恢复仅聊天档。

本 Skill 的可执行默认路线不是打开 Hermes 通用 `file` 或 `terminal`，而是接入 `scripts/scoped_knowledge_mcp.py`。Agent 先解析用户批准目录、知识库外的私有状态目录和 Hermes 安装自带且已验证能导入 `mcp` 的 Python 绝对路径，再执行当前 CLI 的 `mcp add`；用户不填写命令、路径占位符或环境变量。首次只读时不传 `--write`，用户后来明确选择“允许创建和修改”才重新配置写入模式：

```bash
hermes -p <Profile> mcp add bwa_scoped_knowledge --command <Hermes Python绝对路径> --args <Skill绝对路径>/scripts/scoped_knowledge_mcp.py --root <批准的知识库绝对路径> --state-dir <知识库外私有状态目录>
```

`mcp add` 会在发现工具后询问是否启用。Agent 必须在可信 TTY 中代用户处理这个交互，先核对服务器名和精确工具清单，再输入 `Y`；只读模式应只有列出、搜索、读取 3 个工具，写入模式才增加创建、更新和回滚成为 6 个。名称、数量或参数与本轮选择不一致就取消，不能让小白打开终端，也不能把非交互命令退出当成已经保存。飞书和编程 MCP 同样遵守这条门禁：固定文档只读只出现读取工具，锁定创建位置后才多出创建工具；受控 Codex 必须精确出现检查项目、准备、检查变更、应用和回滚 5 个工具。

这个执行器只暴露列出、搜索、读取 `.md` / `.txt`；写入模式才增加创建、带旧版 SHA-256 的更新和回滚。知识库外的状态目录用于保存回滚记录，POSIX 环境必须收紧并复核为当前运行账号所有、`0700`，否则停止。列出、搜索和读取会在把文件名、正文或命中片段交给当前模型前逐次确认；拒绝时不访问知识库。每次写入与回滚也在发起请求的同一界面单独确认：微信里按提示回复 `/approve` 或 `/deny`，Hermes/Codex 桌面若显示确认菜单就按当前菜单选择，在其他窗口预先批准无效。Hermes 已返回 `accept` 时，即使确认内容是空对象也表示这次已经批准；执行器仍以 action 为准，不能误报“确认通道没有返回”。同名创建、目录穿越、隐藏路径、符号链接、超大文件、版本冲突都会拒绝。它没有通用删除工具，回滚只处理自己创建的变更，文件出现后续修改时拒绝覆盖。若当前 Hermes 的 MCP elicitation（操作确认）不能在 Weixin 中真实显示并接收确认，不启用知识库 MCP，不能用 SOUL 中一句“先问我”代替。

每个知识库 MCP 保存后，Agent 必须在同一 Profile 设置并读回三项超时：`approvals.timeout=120`、`mcp_servers.<名称>.elicitation.timeout=120`、`mcp_servers.<名称>.timeout=150`。前两项保持一致，避免确认回调退出后留下仍在等待的旧审批；工具总超时多留 30 秒，让服务器能先返回“已拒绝或已超时”的可操作错误，而不是 Hermes 抢先报笼统的 300 秒工具超时。设置后重载 MCP 或安全重启同一 gateway，再在发起请求的同一界面验证一次批准成功、一次拒绝不读取、一次不回复在 2 分钟后明确取消。`/approve` 不是预先开启权限的开关：它只能批准当前微信里仍在等待的请求；若收到“没有待批准的命令”，说明请求已超时、被拒绝或随 gateway 重启而失效，Agent 必须让用户重新发送原问题，等新的确认提示出现后再在同一微信会话回复 `/approve`。未收到微信入站审批日志时，只能报告“批准没有到达当前微信会话”，不得归因于飞书网络、登录或文档过大。

云端 Hermes 无法直接访问本机 vault；必须先按 `cloud-deployment.md` 选择持续同步方案。

### 飞书

优先使用飞书/Lark 官方 OpenAPI MCP。它仍可能处于 Beta，执行前查看当前官方文档、版本和能力限制。

用户说“飞书已经登录”时，先确认并复述这个事实，不得再次要求输入账号密码。但要用小白能懂的话区分两件事：**账号已登录**只表示当前浏览器或 CLI 认识这个用户；**当前助手的专用应用已就绪**还需要独立应用创建完成、最小权限授权完成并通过真实读取。用户不负责手工建应用、找权限或复制 App ID / App Secret；用户只在飞书官方页面确认当前登录账号、授权范围以及发布或管理员审批等必须由账号本人完成的动作。

只有用户已经选择飞书渠道后，才在微信助手实际运行的目标环境检查 `lark-cli`，不得在知识库渠道选择前安装它或 Docker。检查时只读取非秘密状态：Node/npm 是否可用、Node.js 真实可执行文件与 `lark-cli` 的绝对路径和版本、`lark-cli docs +fetch --help` 是否支持当前 Docs v2 读取，以及当前 Profile/登录状态；输出必须遮住 App Secret 和 token。Node.js 必须解析为已核验、可执行且非符号链接的真实绝对路径，并先实际执行该绝对路径的 `--version`，再执行一段无外部输入的 JavaScript 身份探针，核对 `process.release`、`process.versions` 和 `process.execPath` 都与同一个文件一致；任一步不符就拒绝，不能把 `/bin/sh`、只会伪造版本字符串的脚本或其他任意可执行文件冒充 Node.js。后续交接器和 MCP 都显式传入这一路径，不能依赖 Agent 或隔离 Gateway 继承到的 `PATH`，否则本机终端可读而微信模型层可能稳定失败。按三种状态处理：

- **已有兼容版本**：复用这份确切的 `lark-cli`，不因为有更新就强制升级。为当前助手使用 `--name` 新建独立命名 Profile，不覆盖现有飞书应用和用户会话；之后再创建专用应用并申请最小权限。
- **没有安装**：说明 `lark-cli` 是飞书官方命令行连接器，不是知识库，也不要求 Docker。先检查 Node.js/npm；缺少时一次说明依赖、安装位置与影响并取得用户同意。用户同意后，只使用官方当前安装路线 `npx @larksuite/cli@latest install`，再验证可执行文件绝对路径、版本和 `docs +fetch --help`。用户拒绝安装时暂停飞书能力，基础微信助手保持可用。
- **不确定**：只在目标环境做上述精确检查，不扫描其他电脑、浏览器配置或账号。查不到就按“没有安装”解释，不让用户自己找命令。

官方安装命令中的 `latest` 只表示安装当日从官方包读取当前版本，文档不得把某个现场版本号写成永久最低版本。创建应用由 Agent 使用 `scripts/launch_feishu_oauth.py init --node <Node.js真实绝对路径>` 安全代办；交接器会用这份固定 Node.js 运行时在隔离凭据目录中执行 `lark-cli config init --new --name <独立Profile> --force-init`，等待飞书官方网页完成账号确认，并且不把页面链接、App Secret 或 CLI 原始输出带回对话。若用户已登录，只说明“无需重新登录，请在官方页面确认当前账号”，不能把等待状态误报为登录失败，也不能把旧 Profile 可读误报成新专用应用已完成。

需要用户身份访问个人文档库时，先根据当前命令的真实错误只收集本次动作缺少的 scope，再使用 `scripts/launch_feishu_oauth.py plan --node <同一Node.js真实绝对路径>` 核对 Node.js、Profile、隔离凭据目录、Hermes 根和精确 scope；计划通过后运行同参数的 `launch`。交接器在内存中启动 `lark-cli auth login --no-wait --json`，自动打开飞书官方授权或应用权限页面并等待完成，只输出 `AUTHORIZED` 或“仍需在官方页面确认权限”的安全状态；授权 URL、设备码和 token 不进入聊天、Agent 日志或临时文件。用户只核对当前飞书账号、应用名称与权限文字，不复制链接或设备码。交接器只允许文档读取、文档创建和创建固定知识库父节点所需的最小 scope；需要更多业务权限时必须另行审查，不能用 `--domain all` 代替。

先向用户说明两层不同的授权：飞书“只读权限”只表示不能修改内容，不自动等于“只能读取用户指定的一篇文档”；模型问答还意味着文档内容可能发送给当前模型提供商。首次把私有文档交给外部模型前，必须单独说明目标模型、发送范围和用途并取得明确同意。执行器还要在每次实际读取正文前通过 MCP elicitation 再确认一次，拒绝或通道不支持确认时不得启动飞书进程。用户只同意飞书授权时，不得把它推定为同意发送给模型。

安全流程：

1. Agent 在用户已经登录的飞书官方页面创建专用应用、填写说明并申请最小权限；用户只负责登录、扫码、授权确认或系统要求必须由账号本人完成的动作。不得把创建应用、寻找权限和复制配置步骤重新甩给小白。
2. 只申请当前知识库任务必需的云文档读取权限；写入、创建、移动和删除权限默认不申请，确有需求时另行说明并确认。
3. App ID、App Secret 和用户 token 通过官方复制控件直接进入本地秘密存储或隐藏输入，不让模型读取，不放在聊天或命令参数中。完成后清空临时剪贴板；同时说明这不能保证系统历史或跨设备剪贴板已经删除。
4. 先用应用身份或用户身份真实读取用户指定的一篇文档，再判断飞书实际授权范围。**只读 scope 不是单文档白名单**：如果同一凭据在飞书侧可能读取更广资源，Hermes 前面必须再加本地资源白名单包装器，只暴露固定文档或固定目录的读取工具，并在任何飞书请求发出前拒绝其他 URL、token 和文档 ID。只靠工具说明、SOUL 或“请勿访问其他文档”不算权限边界。
5. 使用当前 `hermes -p <Profile> mcp add --help` 接入该最小读取工具；受保护验收继续通过隔离 runner 执行。`mcp add` 的工具启用提示由 Agent 在可信 TTY 中核对后确认，只读范围只允许读取工具，固定创建位置就绪后才允许再出现创建工具；不得同时暴露通用飞书写入工具或任意文档 ID 的读取参数。
6. 先在工具层完成三项测试：指定文档真实读取成功、无效凭据或服务不可用时给出可操作错误、一个未授权文档链接在联网前被拒绝。不得为了越权测试真实读取另一篇用户没有明确授权的文档。
7. 只有用户明确同意把指定文档发送给当前模型后，才新建会话做模型层问答；最后再从微信真实提问一次。工具成功、模型成功和微信真实回复是三层证据，不能互相冒充。

参考检查：

```bash
hermes -p <Profile> mcp add --help
hermes -p <Profile> mcp list
hermes -p <Profile> mcp test lark
```

权限不足时说明缺少哪一项权限，不建议一次开放全部权限。执行器只显示白名单内的缺失 scope 名称，不回传飞书 CLI 原始失败输出、token 或未知字段；识别不到安全 scope 时只给通用恢复说明。若只能获得空间级或租户级读取而无法建立本地资源白名单，保持知识库能力停用，但不能让失败破坏基础微信助手。

本 Skill 用 `scripts/scoped_feishu_mcp.py` 把飞书凭据和业务范围分开：Agent 先创建一个知识库外、当前运行账号独占的私有目录，再把独立 Profile、固定文档链接、真实 document ID 和可选固定创建位置组成 JSON，通过标准输入交给 `--write-scope <新JSON绝对路径>`；范围文件只能首次创建、POSIX 权限为 `0600`，父目录必须已经是当前账号所有且不向组或其他账号开放。MCP 启动参数只携带 `--node <Node.js真实绝对路径>`、`--scope-file <路径>` 等运行边界，不得出现私人文档链接、document ID 或创建位置 token。每次调用都由这份固定 Node.js 运行时启动 `lark-cli`，并在 `docs` 子命令前显式绑定范围文件中的 Profile，不能依赖当前默认 Profile 或继承的 `PATH`；若应用配置绑定在 Agent 工作区，还必须传入并保留基础闭环已核验的精确 `--hermes-home <Hermes根>`，不得掉回全局配置；文档链接必须是 HTTPS、严格属于 `feishu.cn` / `larksuite.com` 官方域名且使用文档路径，不能只因域名字符串里含有 “feishu” 就放行；其他链接先在本地拒绝。用户没有选择固定创建位置时服务器只注册读取工具，写入工具不会出现在助手能力中。文档正文同样通过标准输入交给 `lark-cli`，不出现在进程命令参数中。Agent 负责用官方页面申请当前动作缺少的最小权限、发布专用应用并配置连接；用户只处理登录和官方授权确认。

创建文档固定使用当前 Docs v2 参数：内容以 `--doc-format markdown --content -` 从标准输入传入；固定文件夹或知识库父节点使用 `--parent-token`，个人文档库使用 `--parent-position my_library`。普通知识空间 ID 不能直接冒充父节点；先在该空间创建或选择一个固定父节点，再把节点 token 写入私有范围文件。现场 `docs +create --api-version v2 --help` 与本段不一致时停止并更新执行器，不用旧版 `--title`、`--markdown`、`--wiki-node` 或 `--wiki-space` 参数试错。

飞书写入不是只读授权的自然延伸。用户选择“允许在飞书创建”后，先说明创建位置、应用身份、创建后不会自动删除以及可能发送给模型的内容范围，再单独申请创建所需权限。每次创建仍需微信内逐次确认；执行器不暴露任意父目录参数、更新、移动或删除工具。先用隔离测试目录完成创建成功、权限不足错误、其他目录在联网前拒绝三项测试；未经用户授权不得用真实私人空间做负向写入。真实飞书创建和真实微信回执都通过，才登记“飞书可写”；仅模拟 CLI 通过只能登记“执行器回归通过”。

## 2. 日常自动化：早安简报、提醒与固定任务

先向用户说明：

> 日常自动化可以让助手在固定时间发送早安简报、天气、AI 日报或提醒，也可以运行一个边界明确的固定任务。你只需要确认“发什么、几点发、发到哪里”；我会把任务建在微信助手实际运行的环境里，先手动执行一次，确认微信真实收到后才算完成。没有可靠实时来源时它会说明失败，不会拿旧内容冒充今天。

第一问只选内容，不先问城市、时间、频率，也不先创建 cron（定时任务）：

> 你最想先自动收到什么？
>
> - **A. AI 日报**
> - **B. 天气或早安简报**
> - **C. 一次或重复提醒**
> - **D. 一个固定任务**
> - **E. 不确定** — 说一件你每天容易忘记或重复做的事，我帮你推荐

用户选定后再判断“已有可复用数据源或任务 / 没有 / 不确定”。已有则先验证并复用；没有则比较官方来源和费用后再配置；不确定则说明每种方案最终会收到什么，不读取外部账号来猜。内容未选定前不得索要城市、时间或投递 ID。任何任务都先手动触发并由微信真实收到，再启用时间表。

这是基础闭环后的正式可选能力，但仍是“用户主动选择才配置”。一次只创建一个 cron 任务，并核对数据源、费用、时区、投递目标、失败行为和停用方法。自定义固定任务若包含发送、发布、购买、删除、外部写入或任意命令执行，必须转入对应高风险能力审查，不能借“定时任务”绕过确认。

先检测 Hermes 当前网页能力、天气工具、Cron、时区、已有任务和投递通道，不输出秘密。再展示以下选项，之后才问城市、推送时间和频率：

| 方案 | 数据与费用 | 特点 | 限制 | 官方地址 |
|---|---|---|---|---|
| 仅 AI HOT 日报 | AI HOT 匿名读取 ¥0；仍消耗模型调用 | 最省钱、信息集中 | 没有天气 | [AI HOT 日报](https://aihot.virxact.com/daily)｜[Agent 接入](https://aihot.virxact.com/agent) |
| 天气 + AI HOT 合并简报 | AI HOT ¥0；天气接口、搜索与模型可能计费 | 一条消息同时看日期、天气和 AI 重点 | 依赖实时天气来源与定时投递 | [AI HOT](https://aihot.virxact.com/) |
| 仅天气提醒 | 天气接口、搜索与模型可能计费 | 内容最短 | 没有 AI 日报 | 使用时展示本次选中天气服务的官网与价格页 |

天气来源不能笼统写“联网查询”。必须先列出当前已配置的数据源；没有时实时比较至少两个可在当前地区使用的官方天气服务，展示免费额度、超额价格、更新频率、定位范围、官网与价格页，再推荐一个。AI HOT 当前公开 Agent 接入为匿名 GET、无需 token 时可标记数据源免费，但模型生成与定时运行仍可能产生费用。AI 日报同样不得只有单一来源：实时核验时至少再比较一个可匿名读取的 AI 新闻来源（如模型厂商官方博客或主流技术媒体的 AI 频道），展示官网、更新频率与免费条件后再推荐；AI HOT 不可用时使用本次已验证的备选源，不回退旧内容。

默认推荐把日期、用户所在城市天气和 AI HOT 的 3–5 条重点合成一条中文消息，减少打扰与模型调用。用户选定方案后再问所在城市、推送时间和是否每天推送。

来源：

- 日期：Hermes 当前系统日期与用户时区。
- 天气：通过已经配置的网页搜索/提取工具查询可靠的实时天气来源。
- AI 日报：[AI HOT](https://aihot.virxact.com/)；每日页面使用 `https://aihot.virxact.com/daily`。

先从健康检查的 `Tool Availability` 确认网页能力，只向用户总结结论：

```bash
hermes -p <Profile> doctor
```

`hermes -p <Profile> tools` 是交互式终端界面，只能在当前工具能够提供真实 TTY 时打开；不要在普通非交互子进程中调用后把失败信息丢给用户。


**Cron 黄金规则：cron（定时任务）必须建在 gateway 运行的环境。**

- 本地路线 → cron 建在本地
- 云端路线 → cron 建在服务器
- **不要两边都建** — 会重复推送同一条消息
- 首次手动投递前执行并读回：`hermes -p <Profile> config set cron.wrap_response false`、`hermes -p <Profile> config get cron.wrap_response`；只有读回 `false` 才继续，避免中文日报外层出现 `Cronjob Response` 和英文管理提示


创建前查看当前 Cron 参数：

```bash
hermes -p <Profile> cron --help
hermes -p <Profile> cron create --help
hermes -p <Profile> cron status
```

能用固定脚本完成的提醒或日报，优先采用 `--no-agent --script`：Agent 只在当前 Profile 的 `scripts/` 目录创建已审核脚本，Hermes 在创建和运行时都会拒绝 `../`、外部绝对路径和符号链接逃逸。只有确实需要模型总结时才使用 Agent cron，并继续受数据源、工具和费用边界约束。脚本失败、空输出和来源过期要给出明确失败，不把旧日报当今天内容。

参考任务：

```bash
hermes -p <Profile> cron create "0 9 * * *" "生成今天的中文早安简报：先读取当前日期和星期；查询<城市>的实时天气并说明温度、天气和一条出行建议；再读取 https://aihot.virxact.com/daily，只选 3 到 5 条今天最重要的 AI 动态，每条保留标题、来源链接和一句话价值。任何来源获取失败都明确说明，不使用旧内容冒充今天，不编造。" \
  --name "早安简报" \
  --deliver "weixin"
```

投递目标用 `weixin` 即可投递到第 4 步设置的 home channel（默认私聊对象），用户不需要填写任何 ID；只有确需投递到非默认会话时才使用 `weixin:<chat_id>`，其中 chat_id 是扫码向导自动填入的 iLink 用户 ID，可通过 `hermes -p <Profile> gateway status --deep` 确认，不要把 chat_id 当作必须手动收集的资料。

把 `0 9 * * *` 替换为用户确认的当地时间，确认 Hermes 时区。若单独配置了便宜的 Cron 模型，使用当前 CLI 支持的 `--model` 与 `--provider` 固定费用边界。

创建后：

1. `hermes -p <Profile> cron list` 检查时间、时区、模型和投递目标。
2. 运行 `hermes -p <Profile> cron run <job_id>` 手动触发一次，再用 `hermes -p <Profile> cron runs <job_id> --limit 5` 核对 durable execution（持久运行回执）为 completed；脚本输出记录必须包含本轮的新鲜标记。不能只看进程退出码：当前 CLI 的部分业务拒绝会打印 `Failed to create job` 但仍返回 0，必须同时检查正向回执、任务清单和运行记录。
3. 在微信确认真实送达、中文格式、日期、天气和 AI HOT 链接。`cron run` 成功只证明任务执行，不证明微信收到。
4. 告诉用户每天会产生的模型、搜索或数据源费用，不能承诺固定金额。
5. 展示并实际验证停用方法：`cron pause <job_id>` 暂停、`cron resume <job_id>` 恢复、`cron remove <job_id>` 移除。Agent 必须使用本轮返回的准确 ID；移除前再次确认，不能按名称猜测。

AI HOT 获取失败时不回退到旧日报；天气无可靠实时数据时不猜。

## 3. 编程智能体

先向用户说明：

> 连接编程智能体后，你可以在微信里描述一个代码任务，专业工具会在你确认的项目中读代码、修改并运行测试，微信助手负责用中文汇报进度和结果。你只需要选择项目，并在每个任务开始前确认范围；默认不会提交代码、推送仓库、发布或部署。助手和代码不在同一台设备时，不能假装已经连通。

第一问先覆盖“已有、没有、不确定”，不得因为维护者电脑上有 Codex 就把 Codex 当作所有用户默认：

> 你现在的情况更接近哪一种？
>
> - **A. 已经在用 Codex**
> - **B. 已经在用 Claude Code**
> - **C. 已经在用 OpenCode**
> - **D. 电脑里有代码，但不知道这些工具是什么**
> - **E. 还没有编程工具或代码项目，只想先体验**
> - **F. 不确定或使用其他工具**

当前发布包只内置 `scripts/scoped_coding_mcp.py` 这一条 Codex 受限执行路线。Claude Code 与 OpenCode 出现在菜单里，是为了复用用户现状并做真实比较，不表示包内已有同等安全的执行适配器；没有补齐“固定项目、隔离修改、两次确认、可回滚、禁止提交/推送/发布/部署”的等价实现和现场验证时，必须停在检测或推荐层，不能把通用终端暴露给微信来凑通。

分支顺序：

- **已经有工具**：获得只读许可后只检查用户选中的工具，确认能否复用；不顺手扫描或安装另外两个。
- **有代码但不懂工具**：先用普通语言解释编程智能体会读代码、修改并测试，再实时比较三种官方方案，只推荐一个。
- **没有工具**：先比较功能、账号、订阅/API 费用和系统支持，用户选定后才安装；不得一次安装多个。
- **没有项目**：让用户选择“创建一个隔离演示项目”或“先暂停”，不得为了测试扫描 Documents 或下载陌生仓库。
- **不确定**：只问平时是否写代码、代码在本机还是云端，不读取项目或登录状态来猜。

无论哪条分支，先选编程工具，再选一个精确项目范围，最后才讨论 Docker、Codex sandbox（代码执行隔离）或其他权限方案。助手、工具和代码不在同一设备时，停止在桥接审查门槛前。

先判断助手运行位置、代码位置和编程工具位置。三者在同一受信设备上才进入普通配置；跨设备必须先解释缺少天然安全通道，并停止在桥接审查门槛前。

用户选定渠道并授权后，才检测对应的 `codex`、`claude` 或 `opencode` 是否安装、能否启动，以及当前 Hermes 是否已有对应内置 Skill；只报告订阅/登录是否可用，不显示 token。找到可执行文件不等于可复用：必须实际运行版本与帮助命令，确认进程能正常退出且受控执行需要的参数仍存在；`scoped_coding_mcp.py` 在每次 MCP 启动时还会机械运行 `codex --help` 与 `codex exec --help`，缺少 `workspace-write`、逐次批准策略、关闭工具联网、临时会话或忽略用户配置所需参数时直接拒绝，不降级为无限制模式。若 npm 版 Codex 的真实入口是 `#!/usr/bin/env node` 启动脚本，隔离 Gateway 不继承用户 PATH，Agent 必须先执行 Node.js 版本与身份探针，再给 MCP 显式传入 `--node <Node.js真实绝对路径>`；不能因为用户终端里 `codex` 能运行就假定微信网关也能找到 Node。Codex 还必须在启用 MCP 前运行 `codex login status`，明确分成“已登录可用 / 未登录 / 登录已失效或凭据不可用”；磁盘里存在 `auth.json` 不能替代当前命令的成功读回。未登录或失效时，Agent 在可信窗口启动当前 CLI 支持的官方登录或 `codex login --device-auth`，用户只在 OpenAI 官方页面确认账号；不得再次在聊天里索要 API key、access token 或让用户粘贴秘密。登录读回成功后才继续。若 macOS 上连 `--version` 都以 137 被系统终止，先只读核对架构、官方包版本和代码签名，把它登记为“已安装但无法启动”；不得反复要求用户登录，也不得默认对官方二进制做临时重签名。Agent 应实时比较官方当前稳定版与安装方式，解释将修复还是升级并取得同意，完成后重新核验；仍不能启动时只提供隔离演示或暂停。然后实时查看官方功能与价格并展示：

Codex 桌面应用显示已登录，不等于 Codex CLI 已登录，两者必须分别以当前 CLI 的 `codex login status` 为准。若用户全局 `~/.codex/config.toml` 已配置 DeepSeek 等自定义 `model_provider`，或通过 `forced_login_method = "api"` 固定了 API 登录，不得覆盖或改写这份全局配置，也不得因此再次索要用户已经配置过的 Key。Agent 应在 Profile 外创建一个仅属于当前运行账号、权限复核为 `0700` 的 Codex 专用登录目录，在可信窗口以 `CODEX_HOME=<专用目录>` 启动官方登录；成功后用同一个 `CODEX_HOME` 读回登录状态。接入时必须给 `scripts/scoped_coding_mcp.py` 传入 `--codex-home <专用登录目录绝对路径>`，由执行器在每次登录检查和 Codex 执行时显式覆盖继承环境。这样只隔离助手的 OpenAI 登录，不改变用户原有 DeepSeek 或其他 Codex 用法。

Hermes 当前内置目录通常提供相应 Agent Skills，但目录和来源标识可能随版本变化。先读取当前目录：

```bash
hermes -p <Profile> skills list --source builtin
```

若目标 Skill 不在内置目录，再使用 `hermes -p <Profile> skills search <名称>`，对搜索结果中的唯一完整来源运行 `hermes -p <Profile> skills inspect <完整来源>`；不要用裸名称安装同名社区 Skill。只安装用户选中的一个。外部 CLI、全局 npm 包、浏览器登录或 API 费用需要另行说明并得到同意。

运行规则：

- 用户在微信提出开发任务时，助手先确认一个 Git 仓库根目录和任务目标；仓库已有未提交修改时停止，避免覆盖用户工作。
- Codex 路线接入 `scripts/scoped_coding_mcp.py`，而不是把 Hermes 通用 `terminal` 暴露给微信。它把项目、Codex CLI、可选的 Codex 专用登录目录、npm 启动脚本需要的 Node.js 真实绝对路径和私有状态目录在安装时锁定，微信工具参数里没有路径或命令字段；状态目录和专用登录目录在 POSIX 环境必须复核为当前运行账号所有、`0700`，否则停止。专用登录目录通过 `--codex-home <专用登录目录绝对路径>` 显式绑定；npm 版启动脚本还要通过 `--node <Node.js真实绝对路径>` 绑定已核验运行时，不能只依赖 Gateway 偶然继承到的 `CODEX_HOME` 或 `PATH`。
- 编程任务记录更新使用同目录临时文件、`fsync` 和原子替换。应用补丁成功但记录保存失败时，执行器立即反向撤销刚应用的补丁，让原项目和旧任务状态都保持未应用；回滚成功但记录保存失败时，执行器立即重新应用原补丁，让项目恢复到回滚前的已应用状态。自动复原也失败时明确要求停止后续修改并人工检查，不能用旧记录冒充当前项目状态。
- Agent 在可信 TTY 中保存 Codex MCP 前，必须核对精确出现 `inspect_code_project`、`prepare_code_change`、`inspect_code_change`、`apply_code_change`、`rollback_code_change` 5 个工具后才确认启用；保存后运行 `mcp list` 与 `mcp test` 读回。随后设置并读回 `approvals.timeout=120`、`mcp_servers.<名称>.elicitation.timeout=120` 和 `mcp_servers.<名称>.timeout=1830`；执行器自身 `--timeout 1800`，MCP 总超时多留 30 秒返回结果，不能沿用知识库的 150 秒或 Hermes 默认 300 秒。
- 登录或额度在任务期间失效时，执行器必须明确说明主项目没有被修改，并引导 Agent 重新检查 `codex login status` 或在 OpenAI 官方页面核对额度；专用 `CODEX_HOME` 的状态数据库不可写时，必须准确提示 Agent 复核目录所有者、`0700` 权限和 gateway 进程写权限，不能误导用户重新登录。不回传 Codex 原始输出，也不让用户在聊天发送 API key 或 token。
- 执行器在每一次 `prepare_code_change` 前都重新运行 `codex login status`；状态无法核验就不创建 worktree，也不调用 Codex。这样安装后会话过期不会变成笼统失败，更不能靠磁盘里残留的认证文件冒充仍已登录。
- `prepare_code_change` 先逐任务说明“哪些代码可能发送给 OpenAI、可能消耗什么额度”，获得确认后在一次性 detached worktree 运行 `codex --sandbox workspace-write --ask-for-approval never -c sandbox_workspace_write.network_access=false exec --ephemeral --ignore-user-config -C <一次性worktree> -`。`--sandbox`、`--ask-for-approval` 和 `-c` 是当前 CLI 的全局参数，必须放在 `exec` 前；同时忽略用户级 Codex 配置、关闭网络，不提交、不推送、不发布、不部署。原项目在此阶段必须保持不变。
- 返回变更文件、摘要和补丁 SHA-256 后，`apply_code_change` 必须取得第二次确认，且只在原项目仍是同一 HEAD、工作区干净、补丁校验通过时应用。`rollback_code_change` 仅回滚该任务；项目出现后续修改时拒绝覆盖。
- `workspace-write` 主要约束写入，不应宣传成对本机其他可读文件的绝对保密边界。项目含高敏感资料或用户要求硬读隔离时，先比较 Docker/虚拟机等隔离环境；没有完成现场验证就保持编程能力停用。

Codex 非交互和沙箱参数必须按当日官方文档与现场 `codex exec --help` 复核；旧版本缺少 `--ephemeral`、`--ignore-user-config` 或明确网络关闭能力时不降级为 `danger-full-access`。先用 Agent 创建的无私人内容演示仓库走完“准备不改原项目 → 摘要 → 再确认应用 → 测试 → 回滚/拒绝”闭环，再接入用户项目。真实 Codex 因登录、额度或平台限制未运行时，只能登记模拟执行器通过。

**云端助手连接本机代码：桥接方案**

项目在 Mac 上、助手在云端时，助手不能天然访问本机代码。本 Skill 不创建“同步一个含任意命令的任务文件”、无限期无密码 SSH 或一次授权后永久执行的桥接；这些设计会把微信账号或同步目录变成远程代码执行入口。

需要桥接时停止本可选流程，另行设计并审查：双向身份认证、固定工作区 ID、允许的动作白名单、逐任务确认、并发锁、超时、输出脱敏、审计日志、撤销和离线回退。任一项缺失都不宣称“微信可调用本机 Codex”。


验证：只在同一受信设备或已通过上述独立安全审查的桥接上，完成一个限定工作区、无外部发布的小任务，检查修改、相关测试、审批和中文回执。
